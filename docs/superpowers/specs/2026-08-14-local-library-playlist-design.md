# Flutter 客户端“本地音乐”列表设计

## 目标

在“我的音乐”页面把当前 TuneFlow Service 已下载并纳入本地曲库的音乐显示为第一个只读卡片，名称为“本地音乐”。用户可以进入该列表、播放全部或从任意歌曲开始播放，并能在下载状态变化后看到最新曲库内容。

## 已确认的产品行为

- “本地音乐”显示在“我的音乐”页面第一张卡片，后面继续显示“试听列表”“我的收藏”和用户歌单。
- 数据唯一来源为当前 Service 的 `GET /api/v1/library/tracks`，不从下载任务列表推算，也不保存客户端副本。
- 本地音乐是只读集合：不提供重命名、删除列表、移除歌曲或拖动排序。
- 列表支持播放全部和从任意歌曲开始播放；播放队列包含整个本地列表并保留所选索引。
- 下载管理仍展示任务和进度；“本地音乐”只展示已经进入 Service 本地曲库的歌曲。

## 范围

本次包含：

- “我的音乐”页同时读取歌单和本地曲库，并固定本地音乐卡片的位置。
- 新增本地音乐详情路由和只读详情状态。
- 复用现有封面、歌曲行、播放队列和错误/空状态视觉组件。
- 下载或曲库变化时使本地音乐卡片及详情失效并重新读取。
- 增加仓库接线、控制器、路由、事件和 Widget 的针对性测试。

本次不修改 Service API，不把本地音乐伪造为服务端歌单，不支持编辑本地文件元数据，不新增客户端文件扫描或删除文件能力，也不改变下载任务的生命周期。

## 方案比较

### 方案 A：把本地曲库伪装成普通歌单

客户端构造一个特殊 `PlaylistDetail`，让现有歌单页面直接展示。改动表面最少，但特殊 ID 可能和服务端歌单冲突，且容易误调用重命名、删除、移除和排序接口。

### 方案 B：独立本地音乐入口

新增单独导航项和页面，完全隔离歌单与曲库。边界清楚，但会增加主导航复杂度，也不符合“本地音乐位于我的音乐首卡片”的已确认体验。

### 方案 C：我的音乐聚合页 + 独立只读详情（采用）

“我的音乐”页聚合两类 Service 资源，但点击后分别进入普通歌单详情和本地音乐详情。本地音乐使用独立路由和控制器，共享现有歌曲展示组件。这样既保持首卡片体验，也不会把本地曲库错误地写回歌单 API。

## 数据与模型边界

### Service 资源

- 普通及内置歌单：`GET /api/v1/playlists?includeBuiltIn=true`，详情由 `/api/v1/playlists/{id}` 提供。
- 本地曲库：`GET /api/v1/library/tracks`，解析为 `LibraryTrack`。
- 下载任务：`GET /api/v1/downloads`，仅用于下载管理，不作为本地列表的事实来源。

`LibraryTrack.id` 是本地文件记录标识，`LibraryTrack.track` 是用于展示和播放的歌曲快照。客户端不得假定下载任务 ID、歌曲 ID 和本地文件记录 ID 相同。

### 页面展示模型

“我的音乐”控制器增加一个明确的本地曲库状态，而不是创建带魔法 ID 的 `PlaylistSummary`。页面渲染顺序固定为：

1. 本地音乐卡片。
2. Service 返回的歌单，保持 Service 顺序。

本地音乐卡片使用稳定测试键 `local-library-card`，展示本地曲库歌曲数，并使用第一首具有有效封面地址的歌曲作为封面；没有歌曲或封面时沿用现有默认封面。

## 组件与路由

### 我的音乐控制器

扩展现有歌单列表控制器的职责，使其注入 `PlaylistRepository` 和 `LibraryRepository`，并行读取两类资源。状态分别保存歌单、本地曲库、加载标记和错误，保证其中一个请求失败时仍显示另一个成功资源。

刷新手势和页面重建同时刷新两类资源。创建或删除普通歌单仍只操作 `PlaylistRepository`，不得影响本地曲库。

### 我的音乐页面

页面在歌单网格最前方插入本地音乐卡片：

- 点击本地音乐卡片进入命名路由 `local-library`，路径为 `/library`。
- 点击普通歌单继续进入现有 `/playlists/:id` 路由。
- 本地卡片没有删除菜单；普通内置歌单和用户歌单维持现有权限行为。
- 本地曲库为空时仍显示卡片并标记 `0 首`，让入口稳定可发现。

### 本地音乐详情

新增轻量 `LocalLibraryController`，只负责加载 `LibraryRepository.list()` 和触发播放。详情页面复用现有歌曲行、封面和空/错误状态组件，并明确移除以下能力：

- 重命名列表；
- 删除列表；
- 删除或移除单曲；
- 拖动排序；
- 任何会被解释为“从列表移除”的收藏或删除操作。

播放单曲时向播放器传入完整歌曲列表及当前索引；播放全部从索引 `0` 开始。空列表时禁用播放全部并显示“暂无本地音乐”。

## 刷新与事件同步

客户端为本地曲库增加独立失效版本，并在以下情况触发刷新：

- 收到 Service 的 `library.*` 事件时；
- 收到可能改变本地曲库的 `downloads.*` 事件时；
- 用户手动刷新“我的音乐”或本地音乐详情时；
- 重新进入相关路由或切换 Service 连接时。

路由键应包含本地曲库失效版本，使当前正在显示的“我的音乐”或本地音乐详情能够重建并读取权威数据。即使当前 Service 版本不发送 `library.*` 事件，`downloads.*`、手动刷新和重新进入页面仍提供可用的同步路径。

事件只表示“需要重新读取”，事件载荷不直接写入页面状态，避免下载任务快照与本地曲库事实来源产生分叉。

## 错误处理

- 歌单成功、本地曲库失败：继续显示歌单和稳定的本地卡片；卡片标记“暂不可用”，进入详情后显示加载错误并提供重试。
- 本地曲库成功、歌单失败：继续显示本地音乐卡片和内容，同时展示歌单加载错误。
- 刷新失败且已有旧数据：保留旧数据并标记为过期，不清空列表。
- Service 返回无效 `LibraryTrack`：沿用严格响应解析，显示加载错误，不静默伪造字段。
- 播放失败：沿用现有播放器错误反馈，不改变本地曲库状态。
- 连接切换：丢弃上一台 Service 的页面控制器和数据，由新连接重新读取。

## 测试与验收

### 控制器测试

- 歌单与本地曲库并行加载成功。
- 任一资源失败时保留另一资源。
- 已有数据刷新失败时保留旧数据并标记过期。
- 本地详情单曲播放传入完整队列和正确索引。
- 空本地曲库不会触发播放。

### Widget 与路由测试

- 本地音乐始终是“我的音乐”的第一张卡片。
- 空曲库仍显示 `local-library-card` 和 `0 首`。
- 本地卡片没有删除入口，普通歌单行为不回归。
- 点击本地卡片进入 `/library`，普通歌单仍进入 `/playlists/:id`。
- 本地详情不存在重命名、删除、移除和排序控件。
- 移动与桌面布局均可展示、刷新和播放本地音乐。

### 事件测试

- `library.*` 增加本地曲库失效版本。
- `downloads.*` 同时使下载页面和本地曲库失效。
- 普通 `playlists.*` 与 `playlist.*` 事件仍保持原行为。
- 重复或乱序事件继续由现有序列保护拒绝。

### 验证

运行相关仓库、控制器、路由、事件和 Widget 测试，再运行覆盖改动文件的 Flutter 静态分析。若设备和 Service 可用，额外验证：完成一首下载后无需重启客户端即可在本地音乐列表出现；删除或移除服务端本地文件后列表同步消失。

## 风险与约束

- 当前工作树已有用户未提交修改，实施必须使用小范围补丁，避免覆盖歌单、播放器、设计组件和测试中的现有改动。
- Service 是否发送 `library.*` 事件需要在实施时用实际事件或 Service 契约确认；不能只依赖该事件完成刷新。
- 本地音乐的删除能力不在本次范围。下载任务删除是否同时删除本地文件由 Service 决定，客户端只重新读取最终曲库状态。
- 不使用特殊歌单 ID 可避免与用户或 Service 内置歌单冲突，并防止对本地曲库误发写操作。
