# TuneFlow 产品 README 设计

## 目标

将客户端 README 从技术联动说明改为面向普通音乐用户的产品介绍。读者首先看到 TuneFlow（音流）的界面、主要体验和下载入口；服务端关系与开发说明只在后半部分简要保留。

README 的首要动作是获取客户端。整体语气应有音乐氛围，同时保持简洁、克制和亲切，不使用夸张宣传语、虚构数据或复杂技术术语。

## 信息结构

采用 Hallmark 的 Workbench 产品导览结构，以真实应用渲染截图作为主要内容。

1. **产品开场**
   - TuneFlow 图标、中文名“音流”和一句简短产品描述。
   - 提供“获取最新客户端”和“了解服务端”两个清晰入口。
   - 不在首屏解释 API、数据流或仓库架构。

2. **桌面体验**
   - 使用桌面首页截图作为主视觉。
   - 用短文案说明首页聚合最近播放、下载和个人歌单。

3. **核心体验**
   - “发现音乐”：搜索、歌单和排行榜入口。
   - “统一管理”：收藏、个人歌单、下载和本地音乐。
   - “沉浸播放”：播放器、歌词、队列和跨尺寸适配。
   - 每项只保留一到两句用户语言，不展开实现细节。

4. **移动体验**
   - 并排展示移动播放器与“我的音乐”截图。
   - 说明手机与桌面使用同一套清晰、连续的体验。

5. **下载客户端**
   - 列出 Android、iOS、macOS、Windows 和 Linux。
   - 当前尚无 GitHub Release，因此入口指向最新成功的 GitHub Actions 构建页面，文案如实标注为“最新构建”。
   - 不宣称存在尚未发布的正式安装包或应用商店版本。

6. **简要说明**
   - 用较短篇幅说明客户端需要连接 TuneFlow Service。
   - 保留公开的客户端仓库与服务端仓库链接。
   - 开发启动、测试命令和 API 细节从主 README 移除，后续可放入独立开发文档。
   - 末尾保留自托管、版权和安全提醒。

## 文案原则

- 从用户动作出发，优先使用“听、找、收藏、下载、继续播放”等词。
- 避免“统一 API 契约、provider、repository、SSE、持久化”等工程术语。
- 不枚举第三方音乐平台。
- 不创造用户规模、性能指标、媒体评价或兼容性承诺。
- 段落短，标题少，不用大量徽章和表格制造虚假繁荣感。
